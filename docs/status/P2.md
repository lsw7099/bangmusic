### 테스트가 실제로 실패할 수 있는지 확인

멱등 재요청 처리, 플레이리스트 버전 검사, 표지 픽셀 수 한도를 각각 끄면 해당 테스트가 실패했다(되돌린 뒤 통과).

### 테스트·검토로 찾아 고친 것

- 플레이리스트 소유자가 자기 업로드 표지를 `GET /artwork`로 받지 못했다(곡·앨범 표지만 권한 판정) → 소유자 판정 추가.
- 캐시 정리 후 렌디션이 `404`가 되어 앱이 "곡이 없어짐"으로 오해할 수 있었다 → 파일만 지우고 `410`으로.
- 계약 공백: 입력 검증 `400`이 없던 15개 동작, 모든 동작의 `426`/`503` → 계약에 추가(02장 §6).
- 실패 파일 재분석(P1 알려진 제한 2) → `scan_failures`로 해소.

## 구현한 것

- **변환**: aac_256/aac_128 (AAC-LC/M4A, 스테레오, 48kHz 상한, faststart, 태그·표지 없음), 유형별 동시성 작업 큐(stream 우선), 대기열 한도·디스크 여유 확인, tmp→fsync→크기·SHA-256·길이 측정→rename, 기동 시 tmp·고아 렌디션 정리, 캐시 한도 정리(응답 중 파일 제외), 손실 원본을 더 큰 손실본으로 다시 인코딩하지 않음, 낮은 CPU 우선순위.
- **플레이리스트**: 분수 인덱스 순서, 원자적 편집(add/move/remove), `If-Match`(412/428), `Idempotency-Key`(24시간), 같은 곡 중복 허용, 접근 불가·누락 곡 자리표시자, 모자이크 표지, 업로드 표지(재인코딩·EXIF 제거), 이름 검색.
- **가사**: LRC 파서(여러 시간·`[offset:]`·범위 밖·형식 오류·잘못된 UTF-8 견딤), 사이드카 `.lrc`/`.txt`/`.ko-pron.lrc`/`.ko.lrc`, 내장 가사, 관리자 직접 입력(재스캔이 덮어쓰지 않음), 사용자별 보정값, ETag/304, `has_lyrics`.
- **재생 기록**: `event_id` 멱등, 30초/50% 집계, 최근(커서)·많이 들은 곡(기간), 삭제, 다른 사용자 ID 충돌 시 정보 노출 없음.
- **본인 데이터**: 홈, 계정 삭제(`last_admin` 보호, 개인 데이터 전부 삭제), 내보내기(JSON).
- **운영**: `backup`/`backup list`/`restore`/`maintenance on|off` CLI, 매일 자동 백업(UTC 18시, 14개 보존), 서버 pid 파일, 복원 시 세션 이월·액세스 토큰 무효화.

## 알려진 제한

1. **FN-10**: DB 파일 자체를 잃으면 스냅샷 이후 회전한 리프레시 토큰은 알 수 없어 그 기기는 다시 로그인해야 한다(01장 §4.8). 교체 전 DB가 남아 있는 일반 복원에서는 재로그인이 필요 없다.
2. 가사 규칙은 기존 Windows 앱 `lyrics-core.js`를 보지 못한 채 만든 제안이다 **[확인 필요]**.
3. 변환 처리량은 합성 사인파로 잰 값이다 **[확인 필요: 실제 음악]**.
4. CI는 아직 한 번도 돌지 않았다(원격 저장소 없음).
5. 태그 변경으로 빈 앨범·아티스트의 삭제 통지(tombstone)는 여전히 없다(P1 제한 3). "누락 곡 정리" 관리 기능과 함께 다룰 것.
6. API minor는 0 그대로다. 아직 배포된 적 없는 `/v1`이라 올리지 않았다. 첫 공개 배포 이후의 추가부터 올린다.
