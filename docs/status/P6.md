# P6 진행 보고 (Proxmox 배포 검증)

형식: 05장 §10.4. 작성 2026-10-04. **수용 기준 모두 통과(2026-10-04).** 마감 정리(시험 계정·옛 DB 삭제)는 사용자 실행 대기. 구성 결정은 05장 P6 "[P6 결정]" 항목 참고.

## 구성

| 항목 | 값 |

| 서버 | Proxmox LXC 107 (비특권, 2코어, 1GB, 디스크 8GB), Node 24 + FFmpeg + systemd |

APK 재설치(`install -r`, 데이터 유지) 뒤 앱이 재로그인 없이 `music.example.com`에 "연결됨" → **FN-10 앱 복귀 통과**.

| FN-16 비행기 모드 콜드 스타트 | 통과. 비행기 모드 + Wi-Fi 끔(삼성은 비행기 모드에서 Wi-Fi를 유지하므로 따로 끔) → 앱 강제 종료 후 실행 → "오프라인" 배너, 받은 앨범만 표시, 앨범 탐색·재생("FLAC · 다운로드됨")·싱크 가사(원문+발음)·대기열 |

**설계와 다른 점 ②**: Android에서 앱 강제 종료·Wi-Fi 끊김 뒤에는 바이트 이어받기(206)가 아니라 처음부터(200) 받는다. 패키지는 일시중지(pause)일 때만 이어받기 정보를 남기는데, OS가 작업을 멈추거나 프로세스가 죽으면 남기지 않는다. 결과 파일은 SHA-256으로 검증되므로 정확성 문제는 아니고, 끊긴 곡 하나를 다시 받는 비용이다. **[P6 결정]** 제약으로 받아들이고 03장 §5.10에 적었다(사용자가 판단을 맡김).

**관찰(효율)**: 동기화할 때마다 받은 곡 전부의 가사를 다시 받는다(96곡 → 앱 시작 두 번에 `GET /tracks/{id}/lyrics` 192건). 동작은 맞지만 곡이 많으면 부담. 가사 `version` 비교로 줄일 수 있다(P7 이후 검토).

**시험이 휴대폰에 남긴 것**: 다운로드 96곡·2.68GB(원본 42곡 + 위 결함으로 생긴 AAC 중복 42곡 + Vol.3 AAC 12곡). 시험 전에는 다운로드가 없었다. → 시험 끝에 앱의 "모든 다운로드 삭제"로 지워 시험 전 상태로 돌렸다. 다운로드 음질도 원본으로 되돌렸다.

## 남은 것

- **[해결 2026-10-04] NPM 접근 로그에 미디어 티켓이 남던 문제.** 사용자가 `access_log off;`·`proxy_buffering off;`·HSTS 적용 → 응답에 `Strict-Transport-Security: max-age=63072000; preload`, 시험 요청이 접근 로그에 남지 않음 확인. 적용 전 줄(`mt=` 165줄)은 티켓 수명(12시간)이 지나면 무효. 아래는 당시 기록:
   `proxy-host-4_access.log`에 `mt=` 포함 줄 29개(값은 출력하지 않고 개수만 확인). 서버 로그는 29건 모두 `mt=<redacted>`로 가려져 있다. 02장 §1·05장 §9 위반이므로 NPM → Proxy Hosts → `music.example.com` → Advanced에 `access_log off;`와 `proxy_buffering off;`를 넣고 SSL 탭에서 HSTS를 켜고(지금 응답에 HSTS 없음), 기존 로그 파일의 해당 줄은 지우거나 티켓이 만료(12시간)되기를 기다린다. NPM 설정은 사용자 로그인이 필요해 직접 바꾸지 않았다. 설치 문서 5단계에 반영함.

- **L3(사용자 필요)**: 실기기로 실서버(`https://music.example.com`) 대상 FN-12(재생·탐색·잠금화면·알림·블루투스), FN-15(다운로드 중 앱 종료·재부팅·Wi-Fi 끊김 후 재개), FN-16(비행기 모드 콜드 스타트). FN-10 복원 후 앱이 재로그인 없이 복귀하는지도 앱에서 한 번 확인.
- FN-07 결함 1(빈 마운트 지점 → 첫 요청 503)의 실서버 재확인(선택, 마운트를 한 번 더 빼야 함).
- Docker Compose 설치 경로(구매자용)는 아직 없다. 저장소에 Dockerfile·compose 파일이 없음.
