## 4. 스트리밍

소리는 **앱 기기에서** 재생한다. 서버는 바이트를 제공할 뿐이며 "현재 재생 중" 상태를 갖지 않는다.

### 4.1 렌디션(제공 형식)

렌디션 = `(곡, 미디어 버전, 프로파일)`의 조합에 붙는 **불변** 자원. 같은 렌디션 ID는 항상 같은 바이트다.

- `profile=original`: 원본 파일 그대로. 서버는 캐시 파일을 만들지 않는다.
- `profile=aac_256` 등: 변환본. `/cache`에 파일로 존재한다.
- 원본이 바뀌면(미디어 버전 변경) 옛 렌디션은 `410 rendition_superseded`가 된다. 따라서 탐색·재연결·이어받기 어디에서도 옛 바이트와 새 바이트가 섞이지 않는다.

**원본 형식과 실제 제공 형식은 다른 필드다**: `Track.source_format`(원본) vs `Rendition.container/codec/mime/size_bytes/duration_ms`(실제로 받는 것). UI의 음질 표시는 렌디션 기준으로 한다.

### 4.2 Range / HEAD

| 요청 | 응답 |
| --- | --- |
| `HEAD /media/{rid}` | 200, `Content-Length`, `Content-Type`, `ETag`, `Accept-Ranges: bytes`, `X-Content-Duration-Ms` |
| `GET` (Range 없음) | 200 전체 |
| `GET` + `Range: bytes=a-b` / `a-` / `-n` | 206 + `Content-Range: bytes a-b/total` |
| `Range` + `If-Range: <etag>` 불일치 | 200 전체 (렌디션이 불변이라 실제로는 발생하지 않지만 계약으로 유지) |
| 범위가 길이를 벗어남 | 416 + `Content-Range: bytes */total` |
| 여러 범위(`bytes=0-1,5-9`) | 200 전체(다중 범위 미지원) |

서버 구현 규칙: 파일을 열어 얻은 디스크립터의 `fstat` 크기가 렌디션의 `size_bytes`와 다르면 응답을 시작하지 않고 원본 변경으로 처리(→ 재스캔 예약, 410). 응답 도중 읽기 오류가 나면 연결을 끊는다(잘린 본문을 정상 종료로 보내지 않는다 → 클라이언트는 `Content-Length` 불일치로 감지).

### 4.3 탐색(seek)

- 플레이어가 Range 요청으로 처리한다. 서버에 탐색 API는 없다.
- FLAC·M4A는 색인/탐색표를 써서 몇 번의 Range 요청으로 위치를 찾는다. 변환본 M4A는 `moov`를 파일 앞에 두어(`+faststart`) 첫 요청만으로 재생·탐색이 가능하게 한다.
- 헤더 없는 VBR MP3는 탐색이 부정확할 수 있다. 서버가 원본을 고치지 않으며, 알려진 제한으로 문서화한다.
- UI의 전체 길이: 플레이어가 길이를 보고하면 그 값, 그 전에는 `Rendition.duration_ms`.

### 4.4 세션 만료와 재생

| 상황 | 동작 |
| --- | --- |
| 재생 중 액세스 토큰 만료 | 미디어 요청은 티켓으로 인증하므로 영향 없음 |
| 재생 중 미디어 티켓 만료(기본 12시간) | 다음 Range 요청이 `401 ticket_expired` → `GET /renditions/{rid}`(필요하면 토큰 갱신 후)로 새 URL → 현재 위치에서 소스 교체. 버퍼에 남은 분량만큼은 끊김 없이 재생. |
| 리프레시도 만료 | 현재 버퍼까지 재생 후 정지. "세션 만료" 상태(04장 공통 상태). 다운로드된 곡은 계속 재생 가능. |
| 세션 취소됨 | 즉시 다음 요청부터 실패. "접근 취소" 상태(§5.8). |

### 4.5 변환 프로파일

**[결정]** 1차 프로파일 2개, 모두 AAC-LC / M4A(`audio/mp4`), 스테레오, 원본 샘플레이트 유지(48kHz 초과는 48kHz로).

| 프로파일 | 비트레이트 | 용도 |
| --- | --- | --- |
| `aac_256` | 256 kbps | 기기가 원본 형식을 재생하지 못할 때의 기본, "고음질" 선택 |
| `aac_128` | 128 kbps | 셀룰러/저장 공간 절약 |

- 인코더는 FFmpeg 내장 `aac`. `libfdk_aac`는 재배포 조건 문제로 쓰지 않는다(05장 §8.5).
- 요청 품질이 변환 프로파일이어도 **원본 비트레이트가 더 낮고 기기가 원본을 재생할 수 있으면 원본을 준다**(손실 원본을 더 큰 손실본으로 다시 인코딩하지 않는다).
- 변환본의 길이는 인코더 지연 때문에 원본과 수십 ms 다를 수 있다. `Rendition.duration_ms`는 변환 결과를 ffprobe로 측정한 값이다.
- 태그·표지는 변환본에 넣지 않는다(`-map_metadata -1 -vn`). 메타데이터는 API가 제공한다.

**[대안]** 변환하면서 동시에 흘려보내는 방식(청크 전송): 시작은 빠르나 `Content-Length`가 없어 Range·탐색·이어받기·무결성 검증이 모두 불가능해진다. 채택하지 않는다. 대신 **파일 전체를 먼저 변환해 캐시에 두고 Range로 제공**하며, 그동안 앱은 "준비 중" 상태를 보인다.

### 4.6 변환 작업 한도와 캐시

| 설정 | 기본값(가정, P2에서 측정 후 조정) | 설명 |
| --- | --- | --- |
| `TRANSCODE_ENABLED` | `true` | `false`면 `features`에서 `transcode` 제외, 재생 불가 형식은 `422 no_playable_format` |
| `TRANSCODE_CONCURRENCY` | `min(2, CPU 코어 수)` | 동시 FFmpeg 프로세스 수 |
| `TRANSCODE_QUEUE_MAX` | 20 | 초과 시 `429 transcode_queue_full` |
| `TRANSCODE_TIMEOUT_S` | 600 | 초과 시 프로세스 종료, `transcode_failed` |
| `CACHE_MAX_BYTES` | 10 GiB | 초과 시 `last_access_at`이 오래된 변환본부터 삭제 |
| `CACHE_MIN_FREE_BYTES` | 1 GiB | 디스크 여유가 이보다 적으면 새 변환 거부 |

**P2 측정 (2026-10-02, Proxmox 비특권 LXC 2코어·RAM 1GB, FFmpeg 7.1.5 내장 `aac`, 합성 음원 5분)** — [확인 필요] 실제 음악은 합성 사인파와 인코딩 비용이 다를 수 있다.

| 경우 | 시간 (5분 음원) | 실시간 배수 | FFmpeg 최대 RSS |
| --- | --- | --- | --- |
| FLAC → aac_256, 단독 | 13.7초 | 약 22배 | 약 57MB |
| FLAC → aac_128, 단독 | 5.5초 | 약 55배 | 약 57MB |
| AAC → aac_256 / aac_128, 단독 | 5.5초 / 4.4초 | 약 55배 / 68배 | 약 58MB |
| 동시 2개 (2코어) | 각각 거의 그대로 (14.2초, 6.2초) | — | 각 약 56MB |
| 동시 3개 (2코어) | 각각 약 1.7배 느려짐, 전체 처리량 증가 없음 | — | 각 약 56MB |

서버 프로세스 RSS는 약 120MB. → 기본값 `TRANSCODE_CONCURRENCY = min(2, 코어 수)`를 **유지**한다(코어 수를 넘기면 처리량은 그대로이고 각 작업만 느려진다). `TRANSCODE_QUEUE_MAX = 20`은 최악의 경우 대기 약 140초(5분 FLAC, 2개 동시)이며 stream 요청이 앞서므로 유지. `TRANSCODE_TIMEOUT_S = 600`은 60분 FLAC(추정 약 165초)에 여유가 있어 유지. 1GB 컨테이너에서 서버 + 변환 2개 ≈ 240MB.

- 우선순위: `purpose=stream` 작업이 `download` 작업보다 먼저 실행된다.
- **[P2 구현]** 캐시 정리는 변환 **파일만** 지우고 렌디션 행은 남긴다. 다음 `GET /renditions/{id}`·미디어 요청이 `410 rendition_superseded`를 받아 앱이 다시 결정(재변환)한다. 행까지 지우면 `404`가 되어 "곡이 없어짐"과 구분되지 않기 때문이다.
- **[P2 구현]** 실패한 변환(`failed`)은 같은 요청을 다시 보내면 한 번 더 시도한다.
- 같은 `(곡, 버전, 프로파일)` 요청이 겹치면 작업은 하나만 만든다.
- 캐시 쓰기: `/cache/tmp/<job>.part`에 쓰고 → fsync → 크기·SHA-256·길이 측정 → `/cache/renditions/<rid>`로 rename → DB에 `ready` 기록. 이 순서 때문에 **불완전한 변환본이 제공되는 일은 없다.**
- 서버 시작 시 `/cache/tmp`를 비우고, `ready`인데 파일이 없는 렌디션 행을 지운다.
- 응답 중인 렌디션 파일은 캐시 정리에서 제외한다(열린 핸들 수 추적).
- FFmpeg 실행: 인자 배열로 직접 실행(셸 미사용), 입력 경로는 경로 해석기가 준 값만, `-nostdin`, 네트워크 프로토콜 비활성(`-protocol_whitelist file`), 낮은 CPU 우선순위.

### 4.7 연결 전환과 끊김

| 상황 | 앱 동작 |
| --- | --- |
| Wi-Fi ↔ 셀룰러 전환, 일시 끊김 | 버퍼로 계속 재생. 소스 오류 시 현재 바이트 위치에서 Range로 재접속(1s, 2s, 4s 백오프, 최대 3회). 재생 상태는 `buffering`. |
| 3회 실패 | 같은 곡의 다운로드본이 있으면 그것으로 전환(위치 유지). 없으면 대기열에서 **다운로드된 다음 곡**으로 넘어가고 스낵바 표시. 재생 가능한 곡이 없으면 일시정지 + "오프라인" 표시. |
| 셀룰러 연결 + "셀룰러 스트리밍 허용" 꺼짐 | 스트리밍하지 않는다. 다운로드본만 재생. |
| 네트워크 종류별 음질 | 설정: Wi-Fi 스트리밍 음질 / 셀룰러 스트리밍 음질 / 다운로드 음질(각각 `original`·`aac_256`·`aac_128`). |
| 서버 주소 2개(집 안/밖) | 서버 프로필은 기본 주소와 보조 주소를 가질 수 있다. 기본 주소 연결 실패 시 보조 주소를 시도하고, 응답의 `server_id`가 프로필과 같을 때만 사용한다. |

다음 곡 준비: 현재 곡 종료 30초 전에 다음 곡의 렌디션을 미리 결정하고 플레이어에 다음 소스로 넘겨 곡 사이 공백을 줄인다. 1차에서 스트리밍 바이트의 영구 캐시는 두지 않는다(다운로드와 책임이 겹치고, 캐시형 오디오 소스는 로컬 평문 프록시가 필요하다).

## 5. 오프라인

### 5.1 원칙

1. 불완전한 파일은 **절대** 재생 대상이나 완료 목록에 나타나지 않는다.
2. 완료 = 길이 일치 + SHA-256 일치 + 최종 경로로 원자적 이동 + DB 기록.
3. 로컬 데이터는 `(서버 프로필, 사용자)`별로 완전히 분리된다.
4. 개인 소유 음원이므로 구독형 서비스식 만료·DRM 규칙을 붙이지 않는다. 파일은 앱 전용 저장소에 평문으로 두며, 이는 **DRM이 아니다**(05장 §8.6).

### 5.2 앱 로컬 데이터 모델

**전역 DB** (`app.sqlite`)

| 테이블 | 컬럼 | 설명 |
| --- | --- | --- |
| `server_profiles` | `profile_id`(로컬 UUID), `server_id`, `name`, `primary_url`, `secondary_url`, `last_api_minor`, `last_features`, `added_at`, `last_used_at` | 사용자가 등록한 서버. `server_id` UNIQUE. |
| `profile_users` | `profile_id`, `user_id`, `username`, `display_name`, `session_state`(`active`/`expired`/`revoked`/`logged_out`), `last_sync_at` | 서버별 로그인 사용자. 토큰은 여기 없고 보안 저장소에 `profile_id+user_id` 키로 저장. |
| `app_settings` | `key`, `value` | 테마, 현재 프로필 등. |
| `entitlement_cache` | `product_id`, `state`, `verified_at`, `source` | 앱 구매 상태(05장 §8.2). **서버 프로필과 무관한 별도 테이블.** |

**프로필·사용자별 DB와 파일**

```text
<앱 전용 저장소>/profiles/<server_id>/<user_id>/
    library.sqlite          곡·앨범·아티스트·플레이리스트·가사 사본, 다운로드, 대기 중인 변경
    media/<track_id>/<rendition_id>.<ext>      완료된 오디오만
    tmp/<download_id>.part                     진행 중 (재생 경로와 분리)
    artwork/<artwork_id>_<size>.<ext>
```

| `library.sqlite` 테이블 | 설명 |
| --- | --- |
| `tracks`, `albums`, `artists`, `playlists`, `playlist_items`, `lyrics` | 서버 응답의 사본. 서버 ID를 그대로 키로 쓴다(프로필별 DB라 충돌 없음). |
| `downloads` | `download_id`, `track_id`, `rendition_id`, `media_version`, `profile`, `state`, `bytes_total`, `bytes_done`, `sha256_expected`, `file_name`, `error_code`, `attempts`, `requested_by`(`track`/`album`/`playlist` + ID), `created_at`, `completed_at`, `stale`(bool) |
| `download_groups` | 사용자가 "앨범/플레이리스트 전체 다운로드"로 고정한 대상. 새 곡이 추가되면 자동으로 받는다. |
| `pending_ops` | 오프라인 중 플레이리스트 편집 연산(순서 보존, `Idempotency-Key` 포함) |
| `pending_play_events` | 미전송 재생 기록(`event_id` 포함) |
| `sync_state` | `changes_since`, 플레이리스트별 `version` |
| `queue_state` | 대기열 스냅샷(§6.7) |

**서버 프로필 분리 규칙**

- 곡 ID·플레이리스트 ID는 서버마다 독립이므로, 앱의 모든 참조는 암묵적으로 `(server_id, user_id)` 범위 안에 있다. 다른 프로필의 캐시·다운로드·대기열을 재사용하지 않는다.
- 프로필 전환 시 재생을 멈추고 대기열을 해당 프로필의 것으로 교체한다. 서로 다른 서버의 곡을 한 대기열에 섞지 않는다.
- **주소는 같은데 `server_id`가 달라진 경우**(서버 재설치, 주소 재사용, 위장 서버): 저장된 토큰을 보내지 않는다. "이 주소의 서버가 이전과 다릅니다" 경고 후 새 프로필로 등록할지 묻는다. 기존 프로필의 다운로드는 그대로 둔다.
- `server_id`는 인증 없이 얻는 값이므로 서버 신원의 근거는 **TLS 인증서**다. `server_id`는 캐시 분리 키일 뿐이다.
- **[P4 구현]** 앱은 토큰을 붙이는 첫 요청 전과 연결이 끊겼다 돌아온 뒤마다 인증 없이 `GET /server`로 `server_id`를 확인한다. 다르면 토큰을 붙인 요청을 보내지 않고(요청은 앱 안에서 실패 처리), 화면은 오프라인처럼 받은 음악으로 그리며, "이 주소의 서버가 이전과 다릅니다" 배너에서 새 서버로 등록하게 한다. 확인 요청 자체가 실패하면 토큰을 보내지 않고 연결 실패로 처리한다. 로그인 화면의 같은 경고(04장 S1)와 함께 FN-21의 "토큰이 전송되지 않음"을 만족시키는 장치다.

### 5.3 다운로드 상태 기계

```text
            ┌────────────────────────── 사용자 취소 → (삭제) ───────────────────────────┐
            │                                                                           │
 queued ─▶ resolving ─▶ preparing ─▶ downloading ─▶ verifying ─▶ completed ─▶ (stale)   │
   ▲           │            │          │   ▲  │           │                      │       │
   │           │            │          ▼   │  └─▶ waiting_network / waiting_wifi / waiting_space
   │           │            │        paused                │                      │
   │           └────────────┴──────────┴──────────────────┴─▶ failed(code)        │
   └──────────────── 재시도(자동/수동) ◀──────────────────────────┘                │
   └──────────────── 새 버전 받기 ◀───────────────────────────────────────────────┘
```

| 상태 | 의미 | 사용자에게 보이는 것 |
| --- | --- | --- |
| `queued` | 대기 | 대기 |
| `resolving` | 렌디션 결정 요청 중 | 대기 |
| `preparing` | 서버 변환 대기(202) | "서버에서 준비 중" |
| `downloading` | 수신 중 | 진행률 |
| `paused` | 사용자가 멈춤 | 일시중지됨 |
| `waiting_network` / `waiting_wifi` / `waiting_space` | 조건 대기 | "연결 대기" / "Wi-Fi 대기" / "저장 공간 부족" |
| `verifying` | 길이·해시 검증 중 | "확인 중" |
| `completed` | 재생 가능 | 완료 표시 |
| `failed(code)` | 자동 재시도 소진 또는 재시도 불가 오류 | 사유 + 재시도 버튼 |
| `stale`(완료의 부가 표시) | 서버에 새 버전 있음 | 재생 가능 + "업데이트 있음" |

| `waiting_login` | 세션 만료(§5.8)로 멈춤. 같은 사용자로 다시 로그인하면 `queued` | "로그인 필요" |

`paused`와 `failed`와 `waiting_*`를 한 상태로 뭉치지 않는다. 화면에서 원인별로 다르게 안내해야 하기 때문이다.

**[P4 구현 결정]**
- `waiting_login`을 추가했다. 04장 S9가 세션 만료 시 진행 중 항목을 "로그인 필요"로 멈추라고 하는데 위 표에 대응 상태가 없었다. 접근 취소·로그아웃 보관은 상태가 아니라 행의 `locked` 표시다(완료본도 잠기므로).
- 상태 기계는 순수 함수 `(행, 사건) → (새 행, 효과 목록)`이다(`app/lib/domain/download_state.dart`). 파일·네트워크·DB 작업은 효과로만 나타나고 엔진이 실행한다. 효과는 "저장 전"(파일을 최종 위치로 옮기기)과 "저장 후"(파일 지우기)로 나뉘어 §5.9의 쓰기 순서 규칙을 지킨다.
- 자동 재시도 대기 중인 항목은 `queued` + `not_before`(다음 시도 시각)다. 별도 상태를 두지 않는다.
- §5.9 "완료인데 파일 없음"은 `failed(file_missing)` 표시 대신 **사유를 남긴 채 `queued`** 로 되돌린다(같은 문단의 "자동 재다운로드 대기열에 추가"를 우선). 화면은 사유가 있으면 "다시 받는 중: 파일 없음"으로 보여 준다.

### 5.4 중단·재개·버전 교체

- 다운로드 URL은 불변 렌디션을 가리키므로 `Range: bytes=<bytes_done>-`로 이어받는다. `If-Range: <etag>`도 함께 보낸다.
- 응답이 `206`이 아니라 `200`이면 부분 파일을 버리고 처음부터 쓴다.
- `410 rendition_superseded`: 부분 파일 삭제 → `resolving`으로 돌아가 새 렌디션으로 처음부터. **옛 바이트에 새 바이트를 이어 붙이는 경로는 없다.**
- `401 ticket_expired`: 렌디션 재조회로 새 URL, 같은 오프셋에서 재개.
- 자동 재시도: 네트워크 오류·5xx는 백오프(5s, 30s, 2m, 10m, 최대 5회) 후 `failed`. 연결 복귀 이벤트가 오면 `waiting_network` 항목을 즉시 재개.
- 동시 다운로드 수: 기본 2(설정 1~4).
- 중복 방지: `(track_id, media_version, profile)`이 같은 다운로드는 하나만 존재한다(UNIQUE). 앨범과 플레이리스트가 같은 곡을 요구하면 파일 하나를 공유하고 `requested_by`만 늘린다. 마지막 요청자가 사라질 때 파일을 지운다.

**완료본의 버전 교체**

1. 동기화에서 곡의 `media_version`이 완료본과 다르면 `stale=true`로 표시한다. **옛 파일은 계속 재생 가능**하다(오프라인 재생이 갑자기 끊기지 않게).
2. "다운로드 자동 업데이트" 설정이 켜져 있고 네트워크 조건이 맞으면 새 렌디션을 별도 다운로드로 받는다.
3. 새 파일이 `completed`가 된 뒤에 옛 파일과 행을 지운다. 재생 중인 파일이면 재생이 끝난 뒤 지운다.
4. 곡이 서버에서 영구 삭제(tombstone)되면: 다운로드본은 "서버에 없음"으로 표시하고 유지한다. 사용자가 지우거나 설정 "서버에서 삭제된 곡의 다운로드 자동 정리"(기본 꺼짐)로 정리한다.

### 5.5 무결성과 불완전 파일 보호

- 수신 중인 바이트는 `tmp/<download_id>.part`에만 쓴다. `media/` 아래에는 완료본만 있다. 플레이어와 완료 목록은 **DB의 `state=completed` 행**만 본다(디렉터리를 훑어 재생 대상을 찾지 않는다).
- `verifying` 단계: (1) 파일 크기 = `size_bytes`, (2) SHA-256 = `sha256_expected`. 해시는 UI 스레드가 아닌 곳에서 스트리밍 계산한다.
- 통과: `media/<track_id>/<rendition_id>.<ext>`로 같은 파일시스템 내 rename → DB 트랜잭션으로 `completed`.
- 불일치: 파일 삭제 후 처음부터 1회 재시도. 다시 불일치면 `failed(integrity_mismatch)`.
- 서버가 `sha256=null`을 준 경우(해시 계산 전): 크기 검증만 하고 `GET /renditions/{id}`를 한 번 더 조회해 해시가 생겼으면 검증한다. 끝내 없으면 완료 처리하되 `verified=size_only`로 기록한다.
- 재생 시작 시 파일 크기를 다시 확인한다. 다르면 손상으로 보고 해당 다운로드를 `failed(file_corrupt)`로 바꾸고 스트리밍으로 대체한다.

### 5.6 로컬 메타데이터·표지·가사

곡을 다운로드할 때 **같은 트랜잭션 묶음으로** 다음을 로컬에 저장한다. 하나라도 빠지면 오프라인에서 화면이 비기 때문이다.

- 곡·앨범·아티스트 행(이미 동기화되어 있지 않다면).
- 표지: 목록용(256)과 몰입 화면용(1024) 두 크기.
- 가사: `GET /tracks/{id}/lyrics` 전체(세 종류 + 보정값).
- 플레이리스트 단위 다운로드면 플레이리스트와 항목 순서, 플레이리스트 표지.

오프라인에서 가능한 것: 다운로드된 곡/앨범/플레이리스트 탐색, 로컬 검색(제목·아티스트·앨범, 같은 정규화 규칙), 대기열 조작, 재생, 가사 보기, 플레이리스트 편집(대기열에 쌓임), 재생 기록 쌓기.

오프라인에서 다운로드되지 않은 곡은 목록에 흐리게 표시하고 누르면 "오프라인에서는 재생할 수 없음"을 알린다(숨기지 않는다. "오프라인에서 다운로드한 항목만 보기" 필터는 기본 켜짐).

### 5.7 디스크 한도

- 설정 "다운로드 저장 한도": 제한 없음 / 사용자가 정한 크기. 기본은 제한 없음.
- 항상 지키는 여유 공간: 기기 여유 공간이 500MB 미만이 되는 다운로드는 시작하지 않는다(`waiting_space`).
- 시작 전 확인: `size_bytes`를 알고 있으므로 `여유 공간 − size_bytes ≥ 500MB`이고 `사용량 + size_bytes ≤ 한도`일 때만 시작한다.
- 한도를 넘어도 **사용자가 명시적으로 받은 파일을 자동으로 지우지 않는다.** 새 다운로드가 대기할 뿐이다. 다운로드 관리 화면에서 크기순 정렬과 일괄 삭제를 제공한다.
- 쓰기 중 공간 부족 오류: `.part` 유지, `waiting_space`.
- 표지 캐시(다운로드와 무관한 탐색용)는 별도 LRU(기본 200MB).
- Android: 내부 앱 전용 저장소 사용. 다른 앱이 접근할 수 없고 앱 삭제 시 함께 지워진다. OS 백업/기기 이전 대상에서 `profiles/`를 제외한다(다른 기기에서 토큰 없이 파일만 복원되는 상태 방지).

### 5.8 세션 만료 · 접근 취소 · 앱 로그아웃 · 앱 구매 상태

네 가지는 원인도 처리도 다르다. 한 가지로 뭉치지 않는다.

| 상태 | 원인 | 다운로드 파일 | 오프라인 재생 | 스트리밍·동기화 | 복귀 |
| --- | --- | --- | --- | --- | --- |
| **세션 만료** | 리프레시 토큰 수명 종료(`refresh_expired`). 오래 접속하지 않음. | 유지 | **가능** | 불가(배너로 재로그인 유도) | 같은 사용자로 로그인 |
| **접근 취소** | 서버가 명시적으로 거부(`session_revoked`, `account_disabled`) 또는 라이브러리 접근 회수 | 유지하되 **잠금** | 불가(해당 범위) | 불가 | 같은 사용자로 다시 로그인하면 잠금 해제. 라이브러리 접근 회수는 해당 곡만 잠금. |
| **앱 로그아웃** | 사용자가 앱에서 로그아웃 | 확인 창에서 선택. **기본: 이 기기의 다운로드 삭제**. "다운로드 보관" 선택 시 잠금 상태로 보관 | 불가 | 불가 | 같은 사용자로 로그인하면 보관본 잠금 해제. 다른 사용자로 로그인하면 별도 공간 사용. |
| **앱 구매 상태** | 스토어 구매/복원 결과 | **영향 없음** | 서버 인증과 무관. 무엇을 제한할지는 **[미결]**(05장 §8.2) | — | 스토어 복원 |

근거와 한계:

- 세션 만료에서 재생을 막지 않는 이유: 파일은 구매자 소유이고, 만료는 "오래 접속 안 함"일 뿐 권한 박탈이 아니다. 여행 중 오프라인으로 90일을 넘겨도 음악이 사라지지 않아야 한다.
- 접근 취소에서 잠그는 이유: 관리자가 분실 기기나 내보낸 계정을 끊었을 때의 기대 동작이다. 삭제가 아니라 잠금으로 두는 것은 실수로 끊었다가 다시 로그인했을 때 전부 다시 받지 않게 하기 위함이다.
- **한계**: 잠금은 앱이 서버 응답을 받았을 때만 적용된다. 기기가 계속 오프라인이면 다운로드본은 계속 재생된다. 이것은 DRM이 아니며 그렇게 표기하지 않는다. 서버 운영자 문서에 "분실 기기는 세션 취소와 함께 기기 원격 초기화를 사용하라"고 안내한다.
- 서버 측 "오프라인 최대 일수" 같은 정책은 1차에 넣지 않는다.

### 5.9 앱 재시작 복구

앱 시작 시(그리고 다운로드 엔진이 백그라운드에서 앱을 깨웠을 때) 대조 작업을 한다.

| 관찰 | 처리 |
| --- | --- |
| DB `downloading`인데 엔진에 작업 없음 | `.part` 크기를 `bytes_done`으로 삼아 재개 작업 등록 |
| 엔진에 완료 작업이 있는데 DB는 `downloading` | `verifying`으로 전환 후 검증 |
| DB `verifying` | 검증 재실행(멱등) |
| DB `completed`인데 파일 없음/크기 다름 | `failed(file_missing)`로 표시, 자동 재다운로드 대기열에 추가 |
| `tmp/`에 DB에 없는 `.part` | 삭제 |
| `media/`에 DB에 없는 파일 | 삭제(고아 파일) |
| DB `resolving`/`preparing` | 렌디션 결정부터 다시(멱등 API) |

DB 쓰기 순서 규칙: 파일을 최종 위치로 옮긴 **뒤에** `completed`를 기록하고, 삭제는 DB 행을 지운 **뒤에** 파일을 지운다. 중간에 죽어도 위 표로 복구된다.

### 5.10 플랫폼 구현

**Android (1차)**

- `DownloadEngine` 구현: `background_downloader`. WorkManager 작업은 실행 시간 제한(약 9분)이 있어 일시중지/재개 허용 옵션으로 주기를 넘어 이어받게 하고, Android 14+에서는 사용자 시작 데이터 전송(UIDT)을 사용한다. **[확인함 2026-10-03, background_downloader 9.6.3]** `TransferHint.userInitiated`(= priority 0 + allowPause)로 UIDT, 실행 중 알림 필수, 앱 매니페스트에 `RUN_USER_INITIATED_JOBS`·`FOREGROUND_SERVICE_DATA_SYNC` 권한이 있어야 한다(없으면 일반 작업으로 떨어짐, 서비스 선언은 패키지가 병합). 받는 동안은 패키지 자기 임시 파일에 쓰고 완료 시 `tmp/<id>.part`로 옮긴다. 이어받기 정보는 작업 ID별로 패키지가 보관하며, 같은 ID에 새 URL(새 티켓)을 주어 `resume`할 수 있다. Android 쪽 로그에 URL(미디어 티켓)을 쓰지 않는다. 실기기(SM-S948N, Android 16)에서 Wi-Fi 끊김·앱 종료·재부팅 후 이어받기 확인(FN-15).
  **[확인함 2026-10-04, P6 실기기 → 실서버] 제약**: 패키지는 일시중지(pause)로 멈출 때만 이어받기 정보를 남긴다. OS가 작업을 멈추거나(Wi-Fi 조건 불충족 `STOP … constraints`) 프로세스가 죽으면 남기지 않으므로, 그 곡은 §5.4의 Range 이어받기가 아니라 **처음부터(200) 다시** 받는다. 완료본은 §5.5대로 SHA-256을 대조하므로 정확성 문제는 없고 비용은 끊긴 곡 하나(수십~백여 MB)를 다시 받는 것이다. **[P6 결정]** 이 제약을 받아들인다(앱 쪽 Range 전송으로 패키지를 우회하면 백그라운드 실행·UIDT를 직접 다뤄야 해 변경이 크다). 곡보다 큰 단위(앨범 전체)는 받은 곡이 유지되므로 영향이 곡 하나로 제한된다.
  또한 OS가 작업을 멈춘 뒤 패키지가 상태를 알리지 않을 수 있어, 엔진은 연결이 바뀔 때 진행 중인 항목에도 연결 조건을 적용하고(조건 불충족 → 전송 취소 후 `waiting_network`/`waiting_wifi`), 엔진이 시키지 않은 패키지 취소는 `network` 실패로 다룬다(P6에서 "받는 중"에 멈춰 있던 결함의 수정).
- 진행 알림: 묶음 알림 1개(전체 진행률, 일시중지/취소). Android 13+ 알림 권한을 다운로드 첫 시작 시 요청하고, 거부해도 다운로드는 동작한다.
- Wi-Fi 전용: 기본 켜짐. 작업 단위 네트워크 제약으로 지정한다.
- 패키지가 재개를 지원하려면 서버가 `ETag`와 `Range`를 제공해야 한다 → 계약에 포함되어 있다.
- 검증·이동·DB 기록은 패키지가 아니라 **앱의 상태 기계**가 한다(패키지 교체 가능성 유지).

**iOS (향후)**

같은 상태 기계·같은 DB·같은 API를 쓰되 다음이 다르다. Android에서 통과한 테스트를 iOS 통과로 간주하지 않는다.

| 항목 | iOS에서의 차이 |
| --- | --- |
| 백그라운드 전송 | 백그라운드 `URLSession`. 앱이 중지돼도 시스템이 전송을 이어 가지만 시작 시점은 시스템 재량이다. 전송 전체에 시스템 자원 제한 시간이 있다. |
| 완료 후 처리 | 완료 시 앱이 잠깐 깨어나지만 시간이 짧다. `verifying`이 다음 앱 실행까지 미뤄질 수 있으므로 UI는 "확인 중"을 정상 상태로 보여야 한다. |
| 티켓 만료 | 백그라운드에서 오래 걸린 전송은 티켓(12시간)이 만료될 수 있다. 401을 받으면 앱이 다음에 깨어날 때 URL을 새로 받아 재개한다. |
| 저장 위치 | Application Support 아래, iCloud 백업 제외 속성 지정. |
| 네트워크 | ATS로 HTTPS 필수(설계와 일치). LAN 서버 접속 시 로컬 네트워크 권한 안내 문구 필요. |
| 형식 | Ogg Vorbis/Opus는 변환 대상(§01 2.7). 앱의 `accept` 목록만 다르게 보내면 서버가 처리한다. |
| 재생 | 백그라운드 오디오 모드, 원격 명령 센터, 지금 재생 중 정보. `PlaybackEngine`의 iOS 구현에서 처리. |

## 6. 재생 상태 모델

### 6.1 상태

```text
idle ─▶ loading ─▶ playing ⇄ paused
            │         │  ▲
            │         ▼  │
            │      buffering
            │         │
            ▼         ▼
          error ◀─────┘        ended (대기열 끝, 반복 꺼짐)
```

| 상태 | 정의 | 잠금화면/알림 표시 |
| --- | --- | --- |
| `idle` | 대기열 없음 | 없음 |
| `loading` | 소스 결정 중(렌디션 결정·변환 대기·파일 열기) | 재생 중 + 로딩 |
| `playing` | 소리 나는 중 | 재생 중 |
| `buffering` | 재생 의도는 있으나 데이터 부족 | 재생 중 + 로딩 |
| `paused` | 정지(사유: `user`, `focus_loss`, `focus_transient`, `noisy`, `error`) | 일시정지 |
| `ended` | 마지막 곡 종료 | 일시정지(위치 0) |
| `error` | 현재 곡 재생 불가(코드 포함) → 자동으로 다음 곡 시도 | — |

`paused`의 **사유를 저장**하는 것이 중요하다. 자동 재개 여부가 사유에 달려 있다(§6.5).

### 6.2 대기열 모델

```text
QueueState {
  context: { type: album|playlist|artist|search|library|adhoc, id? }
  base:    [QueueItem]        // 원래 순서 (컨텍스트에서 온 곡)
  order:   [int]              // 재생 순서 = base의 인덱스 순열
  cursor:  int                // order 내 현재 위치
  up_next: [QueueItem]        // 사용자가 "다음에 재생"으로 끼워 넣은 곡 (FIFO, 셔플 영향 없음)
  shuffle: bool
  repeat:  off | all | one
  position_ms: int
}
QueueItem { queue_item_id(로컬 UUID), track_id }
```

같은 곡이 대기열에 여러 번 있을 수 있으므로 항목 식별은 `queue_item_id`로 한다.

### 6.3 셔플·반복·곡 전환 규칙

**기존 BangMusic의 셔플/반복 테스트가 동작 기준이다.** **[P3]** 기존 앱(v0.4.6, `test/core.test.cjs`의 `nextIndex`)을 확인해 이식했다(`app/test/domain/legacy_port_test.dart`). 다른 점: 기존 앱의 셔플은 매번 무작위로 다음 곡을 고르고(같은 곡이 반복될 수 있고 반복 꺼짐이어도 끝나지 않음), 이 설계는 순열이다. 기존 테스트가 요구하는 것("셔플 다음 곡은 현재 곡이 아님")은 만족하며, 그 밖의 셔플 동작은 테스트가 정하지 않으므로 설계를 유지한다.

| 동작 | 규칙 |
| --- | --- |
| 셔플 켜기 | 현재 곡을 `order`의 맨 앞에 두고 나머지를 Fisher–Yates로 섞는다. 재생은 끊기지 않는다. |
| 셔플 끄기 | `order`를 원래 순서로 되돌리고 `cursor`를 현재 곡의 원래 위치로 옮긴다. |
| 다음 곡(자동) | `repeat=one`이면 같은 곡을 처음부터. 아니면 `up_next`가 있으면 그것 먼저, 없으면 `cursor+1`. |
| 다음 곡(사용자) | `repeat=one`이어도 실제 다음 곡으로 간다. |
| 대기열 끝 | `repeat=all`: 처음으로(셔플이면 다시 섞되 방금 곡이 첫 곡이 되지 않게). `repeat=off`·`repeat=one`(사용자 다음): `ended`, 마지막 곡에 머물고 위치 0. **[P3 갱신]** `repeat=one`에서 마지막 곡의 수동 다음은 기존 앱(`nextIndex`)대로 끝. |
| 이전 곡 | 위치가 3초 초과면 현재 곡 처음으로, 이하면 이전 곡. 첫 곡에서는 처음으로. |
| 대기열 편집 | 순서 변경·삭제·"다음에 재생"·"맨 뒤에 추가". 현재 곡을 삭제하면 다음 곡으로 넘어간다. |
| 새 컨텍스트 재생 | 대기열을 교체한다. `up_next`가 비어 있지 않으면 "대기열을 바꿀까요?"를 묻지 않고 `up_next`를 유지한다. |

난수원은 주입 가능해야 한다(테스트에서 고정 시드).

### 6.4 곡별 소스 선택과 재생 불가 처리

곡을 재생할 때 소스는 다음 순서로 고른다.

1. `completed` 다운로드본(`stale`이어도 사용) — 네트워크 불필요.
2. 온라인이고 네트워크 정책이 허용하면 스트리밍(렌디션 결정 → URL).
3. 둘 다 안 되면 **건너뛴다**.

건너뛰기 폭주 방지: 연속 5곡이 재생 불가이거나 대기열 한 바퀴가 전부 불가이면 정지하고 사유를 한 번만 알린다("오프라인에서 재생할 수 있는 곡이 없습니다" 등). `repeat=all`에서 무한 루프가 생기지 않아야 한다.

### 6.5 오디오 포커스·전화·헤드셋

| 사건 | 동작 | 자동 재개 |
| --- | --- | --- |
| 다른 앱이 영구 포커스 획득(다른 음악 앱) | `paused(focus_loss)` | 안 함 |
| 일시 포커스 상실(전화, 음성 비서, 알람) | `paused(focus_transient)` | 포커스 복귀 시 재개. 단 그 사이 사용자가 직접 일시정지했으면 재개하지 않는다. |
| 덕킹 가능한 일시 상실(내비 안내, 알림음) | 볼륨을 낮춰 계속 재생(시스템 자동 덕킹 사용) | 해당 없음 |
| 유선 이어폰 분리, 블루투스 끊김("noisy") | `paused(noisy)` | 안 함(다시 연결돼도 사용자 조작 필요) |
| 헤드셋/블루투스 버튼 | 재생·일시정지·다음·이전·탐색을 미디어 세션 명령으로 처리 | — |
| 재생 시작 시 포커스 획득 실패 | 재생하지 않고 `paused` 유지 | — |

통화 상태를 읽는 권한(`READ_PHONE_STATE`)은 요청하지 않는다. 오디오 포커스만으로 처리한다.

**[P3 실기기에서 확인한 것]** 일부 기기(SM-S948N, Android 16)는 통화를 "덕킹 가능한 일시 상실"로 보내고, 벨소리가 끝나는 순간 포커스를 잠깐 돌려준다. 재생 패키지의 기본 처리에 맡기면 통화 중에도 음악이 소리가 막힌 채 계속 흘러갔다. 그래서 포커스 사건을 직접 처리한다(`app/lib/domain/audio_focus.dart`).
- 덕킹 신호라도 오디오 모드가 벨소리·통화·VoIP 통화(`AudioManager.getMode()`, 권한 불필요)면 `paused(focus_transient)`.
- 포커스가 돌아와도 아직 통화 모드면 통화가 끝날 때까지 기다린 뒤 재개한다. 그 사이 사용자가 조작하면 재개하지 않는다.

### 6.6 잠금화면·알림·백그라운드

- 재생은 `mediaPlayback` 유형 포그라운드 서비스 + 미디어 세션에서 이뤄진다. UI(액티비티)가 없어도 재생·곡 전환·대기열 진행이 계속된다. 따라서 **대기열 로직은 UI가 아니라 재생 서비스 쪽(오디오 핸들러)에서 실행**된다.
- 세션 메타데이터: 제목, 아티스트, 앨범, 길이, 표지(로컬 캐시 파일). 표지가 아직 없으면 기본 이미지 후 갱신.
- 알림/잠금화면 동작: 이전, 재생/일시정지, 다음, 탐색 막대. 셔플·반복 토글은 사용자 지정 동작으로 추가(공간이 있을 때).
- 일시정지 상태가 오래 지속되면(기본 10분) 포그라운드 서비스를 내려 배터리를 아낀다. 알림은 남겨 재개할 수 있게 한다.
- 최근 앱 목록에서 앱을 밀어 없앨 때: 재생 중이면 계속 재생, 일시정지 상태면 서비스 종료.
- 배터리 최적화로 재생이 끊기는 제조사 기기 대응: 설정 화면에 진단 항목("백그라운드 재생이 끊기나요?")과 시스템 설정 바로가기 제공.

### 6.7 OS가 앱을 종료했을 때

**저장**: `queue_state`에 대기열 전체, `cursor`, 셔플/반복, `position_ms`를 저장한다. 시점: 곡 전환, 일시정지, 대기열 편집 시 즉시 + 재생 중 5초마다 위치.

| 시나리오 | 동작 |
| --- | --- |
| 일시정지 중 프로세스 종료 → 앱 다시 열기 | 대기열·현재 곡·위치를 복원해 `paused`로 표시. 자동 재생하지 않는다. |
| 재생 중 프로세스 강제 종료(메모리 부족 등) | 소리는 끊긴다. 다시 열면 마지막 저장 위치(최대 5초 전)에서 `paused`. |
| 종료 후 헤드셋/블루투스 재생 버튼 | 시스템이 미디어 서비스를 시작 → 저장된 대기열을 복원해 재생 **[확인 필요: 채택 패키지의 재생 재개 지원 범위]** |
| 기기 재부팅 | 자동 시작하지 않는다. 앱을 열면 복원. |
| 복원한 곡이 재생 불가(삭제됨, 오프라인) | §6.4의 건너뛰기 규칙. |
| 다운로드 진행 중 종료 | §5.9. 다운로드는 재생 서비스와 독립적으로 이어진다. |

### 6.8 네트워크가 없을 때

- 앱 시작: 서버에 닿지 못해도 로컬 DB로 즉시 화면을 그린다. 세션 검증을 위해 시작을 막지 않는다.
- 상단에 "오프라인" 표시(04장 공통 상태). 서버가 응답하지 않는 것과 기기에 네트워크가 없는 것을 구분해 문구를 달리한다.
- 재생: §6.4. 대기열에 스트리밍 전용 곡이 섞여 있으면 건너뛴다.
- 변경(플레이리스트 편집, 가사 보정)은 로컬에 즉시 반영하고 `pending_ops`에 쌓는다. 재생 기록은 `pending_play_events`에 쌓는다.
- 연결 복귀: 토큰 갱신 → `pending_ops` 순서대로 전송(충돌 시 02장 §4) → 재생 기록 일괄 전송 → 변경 피드 동기화 → 대기 중 다운로드 재개.

### 6.9 재생 기록 규칙

- ~~한 번의 청취가 30초 이상 또는 곡 길이의 50% 이상이면 재생 1회~~ → **[P3 갱신] 기존 BangMusic 규칙을 따른다**(`test/home-collections.test.cjs`): 곡이 정상으로 불러와져 **재생이 시작되면 1회**. 일시정지·재개·위치 변화로는 늘지 않고, 재생에 실패한 곡은 세지 않는다. 일시정지 상태로 복원만 하고 재생하지 않은 곡은 세지 않는다. 최근 곡은 마지막 재생 시각 순, 많이 들은 곡은 횟수 순.
- 이벤트는 곡이 끝나거나 다른 곡으로 넘어갈 때 만든다. `event_id`는 그때 생성한 UUID이며, 전송 실패 시 같은 ID로 다시 보낸다.
- 탐색으로 건너뛴 구간은 `played_ms`에 넣지 않는다(실제 재생된 시간의 합).
- 재생 기록은 **구매자의 서버로만** 간다.
