## 8. 상용화

### 8.1 판매 모델 후보

**[P7 결정 2026-10-04, 사용자]** **B. 무료 설치 + 1회 구매(비소모성)**. 구매 확인 서버 없음(기기 안에서 스토어 구매 내역으로 확인). 가격은 스토어 등록 때 정한다.

가격, 구독 여부, 구매 확인 서버 필요 여부는 이 설계에서 확정하지 않는다. 설계는 세 후보 모두를 수용하도록 `EntitlementService` 뒤에 격리했다(§8.2).

| 후보 | 구매·복원 방식 | 앱에 필요한 구현 | 판매자 측 서버 | 비고 |
| --- | --- | --- | --- | --- |
| A. 유료 다운로드 앱 | 스토어가 설치 권한을 관리. 복원 = 같은 스토어 계정으로 재설치. | 없음(구매 코드 불필요) | 불필요 | 가장 단순. 체험 기회를 주기 어렵다. |
| B. 무료 설치 + 1회 구매(비소모성) | 스토어 인앱 결제. 복원 = 스토어 구매 내역 조회. | 결제 라이브러리, 구매 화면(S11), 로컬 구매 상태 캐시 | 선택 사항(기기 내 검증만으로 시작 가능) | 체험판 범위를 정해야 한다. |
| C. 구독 | 스토어 구독. 갱신·해지·유예 상태 처리. | B + 구독 상태 처리 | 스토어들이 서버 측 검증을 권장하는 영역. 필요 여부는 정책 확인 후 결정. | 판매자가 지속 제공하는 서비스가 없는 자가호스팅 앱에서 구독의 근거를 설명해야 한다. |

플랫폼별 결제:

- 앱 안에서 디지털 기능을 판매하면 Google Play는 Play 결제 시스템을, Apple은 인앱 결제(StoreKit)를 요구하는 것이 기본 정책이다. 지역별 예외·대체 결제 허용 범위는 변동이 있으므로 출시 국가 기준으로 원문을 확인한다. [Google Play 결제 정책](https://support.google.com/googleplay/android-developer/answer/9858738), [Apple 심사 지침 3.1](https://developer.apple.com/app-store/review/guidelines/#payments)
- 수수료율·가격은 여기서 가정하지 않는다.
- 서버 패키지를 별도로 유료 판매한다면(웹 판매 등) 그것은 모바일 스토어 밖의 별도 상품이다. 앱 안에서 그 구매로 유도하는 문구·링크는 스토어 정책 검토 대상이다 **[미결]**.

### 8.2 구매 권한과 음악 서버 인증의 분리

```text
┌──────────── 앱 ────────────┐
│ EntitlementService         │──── 스토어 SDK ────▶ Google Play / App Store
│   (구매 상태: 로컬 캐시)      │      (선택) 구매 토큰만 ─▶ 구매 확인 서버 [미결]
│                            │
│ ServerProfiles / ApiClient │──── HTTPS ─────────▶ 구매자의 음악 서버
└────────────────────────────┘
        두 경로는 데이터를 공유하지 않는다
```

고정 규칙(판매 모델과 무관):

1. `EntitlementService`는 서버 프로필·토큰·라이브러리에 접근하는 코드 경로가 없다. 반대로 `ApiClient`는 구매 상태를 서버로 보내지 않는다. 음악 서버는 앱 구매 여부를 모른다.
2. 구매 확인 서버를 도입하더라도 전송 항목은 **스토어 구매 토큰/영수증과 상품 ID뿐**이다. 서버 주소, 서버 계정, 토큰, 곡·플레이리스트·재생 기록을 보내지 않는다.
3. 구매 상태는 기기에 캐시하며, 판매자 서버나 스토어에 닿지 못한다는 이유로 재생을 막지 않는다. **개인 서버 재생이 판매자 서버의 상시 접속에 의존하지 않는다.**
4. 구매 상태와 무관하게 항상 가능한 것: 이미 받은 다운로드의 재생, 로그아웃, 다운로드 삭제, 서버 계정 삭제, 데이터 내보내기.
5. 미구매 상태에서 무엇을 제한할지: **[P7 결정]** 서버 연결·탐색·스트리밍 재생·가사·플레이리스트는 무료, **새 다운로드 시작만 구매 후**. 이미 받은 다운로드(구매 상태가 바뀐 뒤 포함)는 4번대로 항상 재생된다. 제한 지점은 `EntitlementService.can(feature)` 한 곳으로 모은다.

서버 패키지와 앱의 분리 제공:

- 서버는 컨테이너 이미지 + Compose 파일 + 설치 문서로 **앱과 독립적으로** 배포·버전 관리한다. 호환성은 API 버전으로 맞춘다(02장 §2).
- 서버 패키지의 라이선스·판매 방식: **[P7 결정]** 무료 배포 + 소스 공개(MIT). 후보와 설계 영향(기록용):

| 후보 | 영향 |
| --- | --- |
| 무료 배포, 비공개 소스 | 이미지에 포함된 제3자 구성요소의 고지·소스 제공 의무는 그대로 있다(§8.5). |
| 소스 공개(허용적 또는 카피레프트) | 앱 판매와 병행 가능. 라이선스 선택이 제3자 포크·호환 클라이언트 가능성에 영향. |
| 유료 판매 | 라이선스 키 검증을 넣는다면 그 검증이 판매자 서버 상시 접속을 요구하지 않게 설계해야 한다. |

어느 쪽이든 서버 코드는 앱 구매를 검사하지 않는다.

### 8.3 개인정보·계정/데이터 삭제

데이터 흐름:

| 데이터 | 저장 위치 | 판매자(개발자)에게 전달 |
| --- | --- | --- |
| 음악 파일, 표지, 가사 | 구매자 서버, 구매자 기기 | 없음 |
| 서버 계정, 플레이리스트, 재생 기록 | 구매자 서버 | 없음 |
| 서버 주소, 토큰 | 구매자 기기(보안 저장소) | 없음 |
| 구매 상태 | 스토어, 기기 캐시 | 없음(**[P7 결정]** 구매 확인 서버를 두지 않음) |
| 오류·사용 통계 | — | **[P7 결정] 수집하지 않음.** (나중에 도입한다면 사용자 동의 후, 서버 주소·곡 제목·사용자 이름 제외, 처리방침·데이터 공개 양식 동시 수정) |

- 기본 설계는 "개발자가 수집하는 개인정보 없음"이다. 분석·오류 보고 SDK를 넣으면 이 전제가 바뀌므로 스토어의 데이터 공개 양식(Google Play 데이터 보안, App Store 개인정보 라벨)과 처리방침을 함께 고쳐야 한다.
- 처리방침 문서에 명시할 것: 앱이 통신하는 상대는 사용자가 등록한 서버와 스토어뿐이라는 점, 서버에 저장된 데이터의 관리자는 서버 운영자(구매자)라는 점.
- 삭제 흐름: 서버 계정 삭제(`DELETE /me`), 재생 기록 삭제, 내보내기, 기기 데이터 삭제(로그아웃/서버 삭제/앱 삭제). 설정 화면에서 모두 도달 가능(04장 S10).
- 스토어의 "계정 생성이 있는 앱은 앱 안팎에서 계정 삭제를 제공해야 한다"는 요구가 구매자 서버의 계정에 어떻게 적용되는지는 **[확인 필요]**. 앱 내 삭제 경로는 위와 같이 제공하고, 웹 경로가 필요하면 서버의 관리 페이지/문서로 대응한다.
- 스토어 심사용 **데모 서버**: 권리가 정리된 합성·자유 이용 음원만 담아 심사 기간 동안 공개 주소로 운영하고, 심사 메모에 주소와 계정을 적는다.

### 8.4 가사·표지·번역 공급자

**[결정] 1차에는 외부 공급자를 내장하지 않는다.** 가사·표지의 출처는 구매자가 서버에 둔 것뿐이다.

| 종류 | 1차 출처 | 규칙 |
| --- | --- | --- |
| 원문 가사 | 곡 옆 `.lrc`/`.txt` 파일, 파일 태그 내장 가사, 관리자 직접 입력 | `source.type`에 기록 |
| 한글 발음 | `<곡이름>.ko-pron.lrc` 파일, 직접 입력, **서버 자동 생성(오프라인)** | **[P3 결정]** 원문에 일본어가 있고 발음 가사가 없으면 서버가 형태소 분석기(kuromoji, IPADIC 사전)로 읽기를 구해 한글로 옮긴다. 기존 Windows 앱과 같은 방식·규칙(조사 は·へ·を → 와·에·오). 외부 서비스 호출 없음. 사이드카·직접 입력이 있으면 그쪽이 우선. 출처는 `generated`로 표시. 이유: 3단 가사가 기존 앱의 핵심 기능인데 발음 파일을 사람이 만들어야 하면 사실상 쓰이지 않는다. 사전 고지(Apache-2.0 + IPADIC 라이선스)는 서버 고지 목록에 넣는다. 구현: 사전은 워커 스레드에 올리고 2분 쓰지 않으면 내린다(측정: 사전 적재 시 RSS 약 +330MB, 내리면 대부분 반환 — 1GB 장비에 상주시키지 않기 위해). 결과는 원문 해시별로 메모리에 캐시 |
| 한국어 번역 | `<곡이름>.ko.lrc` 파일, 직접 입력 | 서버가 자동 번역하지 않는다 |
| 표지 | 파일 내장 이미지, 폴더의 `cover.*`/`folder.*`, 플레이리스트는 업로드 | 외부 검색 없음 |

- **[확인함 2026-10-03, 기존 v0.4.6 코드]** 기존 Windows 앱은 발음을 kuromoji로 **오프라인 생성**하고(이 설계가 서버에서 같은 방식을 쓴다), 가사는 lrclib, 번역은 MyMemory 기계 번역, 표지는 iTunes 검색으로 **외부에서 가져온다**. 외부 세 곳은 이 제품에 넣지 않았다 — 넣으려면 아래 검토 항목을 거친다.
- 가사는 일반적으로 저작물이다. 허가 없는 출처에서 가사를 가져오는 기능은 스토어 심사와 권리 양쪽에서 위험하다.
- 향후 공급자를 추가할 때의 검토 항목(서버의 플러그인 지점: `lyrics.source_type=provider`):
  1. 상업적 이용 허용 여부와 요금
  2. 결과의 저장·캐시 허용 여부와 기간
  3. 출처 표기 의무(→ `source.name`, `license_note`로 앱에 표시)
  4. 호출 한도, 키 관리(판매자 키를 서버 이미지에 넣지 않는다. 구매자가 자기 키를 설정하는 방식 우선)
  5. 번역·발음 변환 결과물의 권리와 재배포 조건
  6. 공급자에게 전달되는 데이터(곡 제목·아티스트)가 개인정보 고지에 반영되는지

### 8.5 오픈소스 라이선스와 고지

프로젝트 자체의 MIT 라이선스는 아래 구성요소의 조건을 대체하지 않는다.

| 구성요소 | 배포 형태 | 조치 |
| --- | --- | --- |
| Flutter 엔진·프레임워크, Dart 패키지 | 앱에 포함 | 앱의 "오픈소스 고지" 화면(Flutter 라이선스 레지스트리로 자동 수집). 릴리스 전 의존성 라이선스 목록 생성·검토. |
| Android/iOS 플랫폼 코덱 | OS 제공 | 앱에 코덱을 넣지 않는다. FFmpeg 디코더 확장을 앱에 넣는 선택은 하지 않는다(라이선스·특허·크기). |
| Node.js 의존성 | 서버 이미지에 포함 | CI에서 라이선스 검사. 허용 목록 밖(GPL/AGPL 등)은 빌드 실패 → 사람이 판단. |
| **FFmpeg** | 서버 이미지에 실행 파일로 포함 | 아래 참조 |
| Caddy, SQLite | 이미지/별도 컨테이너 | 각 라이선스 고지 포함 |
| 기존 Windows 앱의 mpv 바이너리 | **가져오지 않는다** | 모바일·서버 어디에도 포함하지 않는다. |

FFmpeg:

- 서버는 FFmpeg를 **별도 프로세스(CLI)** 로 실행한다. 라이브러리로 링크하지 않는다.
- 이미지에 FFmpeg 바이너리를 넣어 배포하면 그 바이너리의 라이선스 의무(고지, 소스 제공)를 진다. 빌드 옵션에 따라 LGPL 또는 GPL이 되며, `--enable-nonfree` 빌드는 재배포할 수 없다. 배포판 패키지의 FFmpeg는 GPL 옵션으로 빌드된 경우가 흔하다.
- 후보: (a) 필요한 디코더와 내장 AAC 인코더만 켠 LGPL 구성으로 직접 빌드, (b) 배포판 패키지를 쓰고 GPL 의무 이행, (c) 이미지에 넣지 않고 구매자가 설치. `libfdk_aac`는 어느 경우에도 쓰지 않는다.
- **[P7 결정 2026-10-04, 사용자] (b)**. 이미지 기반 배포판의 `ffmpeg` 패키지를 쓰고 GPL 의무를 이행한다: 이미지의 `/licenses/`에 FFmpeg 라이선스 전문·빌드 구성(`ffmpeg -buildconf`)·해당 패키지 버전의 소스 위치(배포판 소스 패키지)를 넣고, 서버 문서에 안내한다. 서버는 별도 프로세스로 실행하므로 서버 코드(MIT)는 GPL이 되지 않는다.
- 이미지에 `/licenses/` 디렉터리로 전체 고지문과 소스 위치를 넣고, 서버 문서에서 안내한다.
- AAC 등 코덱의 특허 라이선스는 저작권 라이선스와 별개 문제다. 상용 배포 전 검토 대상으로 남긴다 **[미결]**.

### 8.6 앱 판매 권한과 음원 배포 권한

- 이 제품에서 판매자는 **소프트웨어만** 판매·배포한다. 음원·가사·표지를 제공하지 않는다. 음원은 구매자가 자기 서버에 둔 것이며, 그 이용 권리는 구매자의 책임이다(이용 약관에 명시).
- 스토어 등록 정보·스크린샷에 "음악을 제공한다"는 인상을 주지 않는다. 스크린샷은 합성 표지·가상의 곡명만 사용한다.
- Google Play와 Apple은 무단 스트리밍/다운로드를 조장하는 앱을 허용하지 않는다. 앱 설명에 "사용자 본인의 서버에 있는 본인 소유 음악을 재생"하는 용도임을 분명히 하고, 타 서비스에서 음원을 내려받는 기능을 넣지 않는다.
- **DRM**: 개인 소유 음원을 대상으로 하므로 DRM을 요구사항으로 두지 않았다. 향후 권리자가 조건을 건 음원을 다루게 되면 다시 판단한다. 앱 전용 저장소 보관이나 파일 암호화는 DRM이 아니며, 문서·스토어 설명에서 그렇게 부르지 않는다.
- 다중 사용자 기능은 가족 등 구매자가 허용한 사람을 위한 것이다. 구매자가 타인에게 음원을 제공할 권리가 있는지는 판매자가 보증하지 않는다.

### 8.7 독자 브랜드와 이미지

- 기존 앱이 참고한 BanG Dream!·Apple Music은 색감·사용성 참고일 뿐이다. 상용 앱에는 그 로고·캐릭터·화면 배치·아이콘 모양을 쓰지 않는다.
- **제품명 "BangMusic"** 은 기존 상표와의 혼동 가능성 검토가 필요하다 **[미결: 상표 조사 후 이름 확정]**. 코드에서 제품명·패키지 ID·서버 `product` 문자열을 상수 한 곳에 두어 이름 변경 비용을 줄인다(패키지 ID는 스토어 등록 후 바꿀 수 없으므로 P3 시작 전에 확정).
- 앱 아이콘·LP 원반 그림·빈 화면 그림은 직접 제작한다. 강조색 값은 04장의 독자 값이다.
- 글꼴은 기기 기본 글꼴(배포할 글꼴 없음).

## 9. 배포와 검증

### 9.1 디렉터리와 권한

```text
VM (Debian)
  /srv/bangmusic/
    compose.yaml
    .env                    (권한 600, 소유자 root)       ← 비밀값 아님: 포트, 경로, 한도
    secrets/                (권한 700)
      signing.key           미디어 티켓 서명 키 (최초 기동 시 생성)
  /mnt/music                읽기 전용 마운트 (ro,nosuid,nodev,noexec)
  /var/lib/bangmusic/data   DB, 업로드, 백업 스냅샷       (서버 UID만 쓰기)
  /var/lib/bangmusic/cache  변환·썸네일 캐시               (서버 UID만 쓰기, 별도 볼륨 권장)
```

```yaml
# compose.yaml 골격 (값은 예시)
services:
  server:
    image: bangmusic/server:1.0.0        # 버전 고정
    user: "10001:10001"
    read_only: true
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    tmpfs: ["/tmp"]
    volumes:
      - /mnt/music:/music:ro
      - /var/lib/bangmusic/data:/data
      - /var/lib/bangmusic/cache:/cache
      - ./secrets:/run/secrets:ro
    env_file: .env
    expose: ["8080"]                     # 외부에 직접 공개하지 않음
    healthcheck: { test: ["CMD", "bangmusic-server", "healthcheck"] }
  proxy:
    image: caddy:2
    ports: ["443:443", "80:80"]
    volumes: ["./Caddyfile:/etc/caddy/Caddyfile:ro", "caddy_data:/data"]
volumes: { caddy_data: {} }
```

- 음악 원본은 VM 마운트와 컨테이너 마운트 **양쪽에서** 읽기 전용이다. 서버 코드에는 `/music` 아래에 쓰는 경로가 없다.
- DB와 캐시는 서로 다른 디렉터리(가능하면 다른 볼륨)다. 캐시가 가득 차도 DB 쓰기가 실패하지 않아야 한다.

### 9.2 비밀값 관리

| 비밀값 | 생성 | 보관 | 금지 |
| --- | --- | --- | --- |
| 티켓 서명 키 | 최초 기동 시 무작위 생성 | `secrets/signing.key`(600) | 이미지에 내장, 환경 변수 출력, 로그 |
| 첫 관리자 비밀번호 | `bangmusic-server admin create`를 대화형으로 실행해 입력 | Argon2id 해시만 DB에 | 기본 비밀번호, 명령행 인자로 전달 |
| TLS 개인키 | 프록시가 발급·갱신 | 프록시 볼륨 | 서버 컨테이너에 노출 |
| DNS API 토큰(DNS-01 사용 시) | 구매자가 발급 | 프록시 전용 env 파일(600) | compose 파일에 평문 |

- 이미지에는 어떤 비밀값도 없다. 저장소에 `.env.example`만 둔다.
- 로그 규칙: 요청 로그에 `Authorization`, 쿠키, `mt`, 비밀번호 필드를 남기지 않는다. 오류 로그의 파일 경로는 서버 로그에만 남고 HTTP 응답에는 넣지 않는다.
- 서명 키를 교체하면 발급된 미디어 티켓만 무효가 된다(앱이 자동으로 재발급받는다).

### 9.3 HTTPS

앱은 HTTPS만 허용한다(릴리스 빌드에서 평문 HTTP 차단). 구매자 환경별 구성:

| 환경 | 인증서 | 비고 |
| --- | --- | --- |
| 공개 도메인 + 포트 개방 | 프록시가 ACME HTTP-01로 자동 발급 | 가장 단순. 인터넷 노출에 따른 보안 책임 안내 필요. |
| 도메인은 있으나 LAN/VPN 전용 | ACME DNS-01(DNS 공급자 API) | 포트를 열지 않고 공인 인증서 사용. |
| VPN 오버레이(메시 VPN 등)의 자체 HTTPS 인증서 | VPN이 제공 | 구매자 문서에 예시로 안내. |
| 사설 CA·자체 서명 | 1차 미지원 **[미결]** | 지원하려면 앱이 사용자 설치 CA를 신뢰하도록 설정해야 하고 보안 설명 UI가 필요하다. "인증서 오류 무시" 기능은 넣지 않는다. |

- 프록시 설정: HSTS, 요청 본문 크기 제한(표지 업로드 한도), 미디어 경로의 응답 버퍼링 끄기, 접근 로그에서 쿼리 문자열 제외.
- 서버는 프록시 뒤에서만 수신한다(`X-Forwarded-*`는 신뢰할 프록시 주소에서 온 것만 인정).

### 9.4 검증 수준 정의

성공 보고는 반드시 **어느 수준에서 확인했는지**를 함께 적는다. 낮은 수준의 성공을 높은 수준의 성공으로 표시하지 않는다.

| 수준 | 환경 | 증명하는 것 | 증명하지 못하는 것 |
| --- | --- | --- | --- |
| L0 | 단위 테스트 | 로직(셔플, 상태 기계, 경로 해석, 파서) | 통합 동작 |
| L1 | 개발 PC의 로컬 서버 + 합성 음원 + 에뮬레이터/모의 서버 | API 계약, Range, 권한, 복구 로직 | 실제 네트워크·저장소·기기 오디오 |
| L2 | Proxmox VM의 실서버(읽기 전용 마운트, HTTPS, 실제 도메인) | 배포 구성, 마운트 장애, 백업 복원, 인증서 | 기기 동작 |
| L3 | 실기기(Android) ↔ L2 서버 | 실제 재생·탐색·백그라운드·블루투스·오프라인 | iOS |
| L4 | iOS 실기기 | iOS 동작 | — |

### 9.5 보안 테스트 (서버, 자동화 대상)

| 번호 | 테스트 | 기대 |
| --- | --- | --- |
| SEC-01 | ID 자리에 `../`, 절대 경로, URL 인코딩된 경로, NUL 바이트 | 400 또는 404. 파일 시스템 접근 없음. |

| SEC-07 | 다른 렌디션용 티켓, 만료 티켓, 변조 티켓, 취소된 세션의 티켓 | 401. |
| SEC-08 | 일반 사용자가 `/admin/*` 호출 | 403. |
| SEC-09 | 모든 오류 응답과 정상 응답 본문에서 서버 경로 문자열 검색(`/music`, `/data`, 실제 루트) | 0건. |

| SEC-12 | 리프레시 토큰 재사용(유예 시간 이후) | 세션 폐기. |
| SEC-13 | 표지 업로드에 초대형 이미지·잘못된 형식·압축 폭탄 | 413/415/400, 서버 생존. |
| SEC-14 | 손상된 오디오 파일 스캔·변환 | 해당 파일만 실패 기록, 프로세스 생존, 시간 제한 준수. |
| SEC-15 | 컨테이너 안에서 `/music`에 쓰기 시도 | 실패(읽기 전용). |

### 10.2 개발용 합성 음원

실제 음원을 저장소·CI·데모 서버에 넣지 않는다. `tools/make-fixtures` 스크립트가 FFmpeg로 생성한다.

```bash
# 예: 10초마다 음높이가 바뀌는 5분 FLAC (탐색 위치를 주파수로 자동 판정 가능)
ffmpeg -f lavfi -i "aevalsrc='sin(2*PI*(220+110*floor(t/10))*t)':s=44100:d=300" \
  -metadata title="夜明けのうた" -metadata artist="テスト楽団" -metadata album="合成アルバム" \
  -metadata TITLESORT="よあけのうた" -c:a flac fixtures/lib1/album1/03-yoake.flac
```

| 묶음 | 내용 | 검증 대상 |
| --- | --- | --- |
| 형식 | MP3(CBR, VBR), FLAC(16/24비트), M4A(AAC), M4A(ALAC), Ogg Vorbis, Opus, WAV | 원본 제공/변환 판정, 기기 재생 |
| 길이 | 1초, 30초, 5분, 60분 | 짧은 곡 전환, 긴 곡 탐색·티켓 만료 |
| 메타데이터 | 한글·일본어(한자/가나/전각/반각)·이모지 제목, 정렬 태그 유무, 태그 없는 파일 | 검색 정규화, 정렬 |
| 표지 | 내장 표지(생성한 단색+숫자 이미지), 폴더 `cover.jpg`, 표지 없음, 아주 큰 표지 | 썸네일, 자리표시자 |
| 가사 | `.lrc`(동기), `.txt`(비동기), `.ko-pron.lrc`, `.ko.lrc`, 깨진 LRC | 3단 가사, 파서 내구성 |
| 이상 파일 | 0바이트, 잘린 파일, 확장자와 내용 불일치, 내용이 같은 중복 파일 | 스캔 내구성, 이동 판정 |
| 경로 | 공백·특수문자·아주 긴 이름, 대소문자만 다른 이름, 루트 밖을 가리키는 심볼릭 링크 | 경로 처리, SEC-02 |
| 라이브러리 2개 | `lib1`, `lib2` | 권한 분리 |

음높이 계단 음원을 쓰면 "탐색 후 재생된 구간의 주파수"로 위치 정확도를 자동 검사할 수 있다(서버 측: 받은 바이트를 디코드해 확인). 실기기 청취 확인용으로는 10초마다 "삑" 횟수가 늘어나는 음원을 추가한다.

### 10.3 단계

각 단계는 앞 단계의 수용 기준을 통과해야 시작한다. "증거"는 완료 보고에 첨부할 것.

**P0. 계약과 환경 (산출물: 저장소 골격)**

- 작업: 저장소 구조(`server/`, `app/`, `openapi.yaml`, `tools/`), OpenAPI 린트를 CI에 추가, OpenAPI → Dart 클라이언트·서버 스키마 생성 파이프라인, 합성 음원 생성기, 미결 항목 중 P1 전에 필요한 것 결정(§README).
- 수용 기준: `openapi.yaml` 린트 통과(L0). 합성 음원 세트 생성 성공. `flutter doctor`에서 Android 툴체인 정상. 빈 Flutter 앱의 디버그 APK가 실기기에 설치·실행됨(L3, 도구 체인 확인용).
- 증거: CI 로그, `flutter doctor -v` 출력, 기기 스크린샷.

**P1. 서버 핵심 (인증·카탈로그·원본 스트리밍)**

- 작업: SQLite 스키마·마이그레이션, 관리자 생성 CLI, 로그인/갱신/취소, 스캐너(영속 ID, 이동 감지, 누락 표시), 곡/앨범/아티스트/검색/변경 피드, 표지 썸네일, 렌디션(`original`)과 Range/HEAD, 미디어 티켓, 오류 형식.
- 수용 기준: OpenAPI 계약 테스트(응답이 스키마와 일치) 통과. SEC-01~12 통과. FN-01, 02, 08 통과. 응답·로그에 경로·토큰 없음. (모두 L1)
- 증거: 테스트 보고서, `curl` 세션 기록.

**P2. 서버 완성 (변환·플레이리스트·가사·기록·운영)**

- 작업: 변환 작업 큐와 캐시, 플레이리스트(버전·충돌·표지), 가사(사이드카 스캔, 3종, 보정), 재생 기록(멱등), 홈, 관리 API, 백업/복원 명령, 저장소 장애 처리, 컨테이너 이미지와 Compose.
- 수용 기준: SEC-13~15, FN-04, 06, 09, 10, 11, 20, 22(서버 측) 통과(L1). 오류 코드 표(02장 §6)의 각 코드를 발생시키는 테스트 존재. 변환 처리량·메모리 사용 측정값을 기록하고 기본 한도 값을 조정. 컨테이너가 비루트·읽기 전용 루트로 기동.
- 증거: 테스트 보고서, 측정 기록, 이미지 구성요소 라이선스 목록.

**P3. Android 앱 골격과 스트리밍**

- 시작 전 확정: 패키지 ID(제품명), `minSdk`, 패키지 버전 고정.
- 작업: 디자인 토큰·컴포넌트, 서버 등록/로그인(S1), 토큰 보안 저장·갱신, 홈/라이브러리/검색/앨범/플레이리스트 조회(S2~S6), `PlaybackEngine`(재생 서비스, 미디어 세션, 대기열·셔플·반복), 미니 플레이어·몰입 화면(S7, S8), 가사 표시, 재생 기록 전송, 서버 버전 호환 처리.
- 수용 기준: `domain/` 단위 테스트(기존 셔플/반복/LRC 테스트 이식분 포함) 통과(L0). 모의 서버 대상 위젯·통합 테스트 통과(L1). **L1 서버 + 실기기**로 FN-05, 12, 13, 14, 18 통과(L3 중 서버는 로컬). 형식별 재생 가능 여부 표 작성(01장 §2.7의 [확인 필요] 해소).
- 증거: 디버그 APK, 실기기 화면 녹화, 형식 표.

**P4. 오프라인**

- 작업: 로컬 DB·프로필 분리, `DownloadEngine`, 다운로드 상태 기계·검증·복구, 다운로드 관리(S9), 오프라인 탐색·검색·재생, 대기 연산 동기화, 세션 만료/접근 취소/로그아웃 처리, 저장 한도.
- 수용 기준: 상태 기계 단위 테스트(모든 전이, 재시작 대조표) 통과(L0). FN-03, 15, 16, 17, 21, 22 통과(L3). 불완전 파일이 재생·목록에 나타나지 않음을 장애 주입으로 확인.
- 증거: 테스트 보고서, 실기기 시나리오 체크리스트(각 항목 통과 일시·기기·OS 버전).

**P5. 화면 상태·접근성 마무리**

- 작업: 04장 각 화면의 상태 표 전 항목 구현, 큰 글씨·가로 화면·스크린리더, 다크/라이트, 동작 줄이기, 설정(S10), 구매 화면 골격(S11, 판매 모델 확정 시 연결).
- 수용 기준: 화면×상태 매트릭스 체크리스트 전 항목 확인(스크린샷 첨부). FN-19 통과. 대비 측정 통과. Android 17 로컬 네트워크 제한을 호환성 플래그로 켠 상태에서 LAN 서버 연결 흐름 확인.
- 증거: 스크린샷 묶음, 접근성 점검 기록.

**P6. Proxmox 배포 검증**

- 필요 입력: Proxmox 접속, VM 사양, 음악 마운트 방식, 도메인/HTTPS 방식. 이 값들이 없으면 시작하지 않으며, P1~P5의 성공을 배포 완료로 표시하지 않는다.
- **[P6 결정, 2026-10-04 사용자]** 실서버는 새 VM이 아니라 **비특권 LXC 107**(Node·FFmpeg 직접 설치 + systemd)을 그대로 쓴다. 음악은 호스트 `/mnt/media/library/music`을 `ro=1` 바인드 마운트(`/srv/music/real`), 읽기 권한은 CT 안 전용 그룹 `music`(gid 1100 = 호스트 101100). HTTPS는 기존 NPM(CT 105) + Let's Encrypt(Cloudflare DNS 인증), 도메인 `music.example.com` → 내부 IP 192.168.1.5(포트 개방 없음, 외부는 WireGuard). 이유: 호스트의 다른 서비스가 모두 LXC이고 메모리(7.5GB)를 아끼려는 사용자 선택. 따라서 이 단계의 L2는 "Proxmox LXC 실서버"이며, Compose(VM) 경로의 검증은 구매자용 설치 문서 단계에서 따로 한다.
- 작업: VM 생성, 읽기 전용 마운트, Compose 배포, HTTPS, 백업 일정, 설치 문서 작성.
- 수용 기준: FN-01, 06, 07, 09, 10을 L2에서 통과. SEC-15를 실서버에서 확인. 실기기로 실서버 대상 FN-12, 15, 16 재확인(L3). 설치 문서만 보고 새 VM에 재설치 성공.
- 증거: 배포 기록, 복원 연습 기록, 실기기 녹화.

**P7. 판매 준비**

- 필요 결정: 판매 모델, 서버 패키지 라이선스, 제품명/상표, FFmpeg 배포 방식, 오류 보고 수집 여부.
  **[결정 2026-10-04, 사용자]** 판매 모델 B(1회 구매, 구매 확인 서버 없음, 미구매는 새 다운로드만 제한), 서버 무료 + MIT 소스 공개, 제품명 BangMusic(상표 조사는 하지 않음), FFmpeg 배포판 패키지 + GPL 의무 이행, 오류·통계 수집 없음, 구버전 앱 지원은 최근 메이저 2개 + 최소 12개월.
- 작업: 릴리스 서명·앱 번들, 결제 연동과 복원(모델 B/C일 때), 개인정보 처리방침·약관, 오픈소스 고지, 스토어 등록 정보·스크린샷(합성 자료), 심사용 데모 서버, 서버 업데이트·롤백 절차 문서, 릴리스 노트 규칙(API minor, `min_client_api_minor`).
- 수용 기준: 서명된 릴리스 빌드로 FN 주요 항목 회귀 통과(L3). 스토어 테스트 트랙에서 구매·복원·환불 후 상태 확인(모델 B/C). 구매 서버·스토어에 닿지 않는 상태에서 다운로드 재생 가능 확인. 서버 구버전→신버전 업그레이드와 롤백 연습 성공.
- 구분: 디버그 APK가 동작하는 것과 판매 가능한 앱은 다르다. 이 단계 전에는 "판매 가능"이라고 표시하지 않는다.

### 10.4 완료 보고 형식

각 단계의 보고는 다음을 포함한다: 통과한 수용 기준 번호와 **검증 수준(L0~L4)**, 실패·보류 항목과 사유, 측정값, 사용한 서버·앱 버전과 기기/OS 버전, 설계에서 벗어난 점과 그 이유(설계 문서 갱신 포함).
